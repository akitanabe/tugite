# 起草手順

ユーザー要求から Implementation Plan の初稿を作る手順を定める。起草はレビューループの入力を作る
工程であり、この時点の完成度で確定しない。弱点はレビューで潰す前提で、主張・仮定・根拠を明示的に
書き残すことを優先する。

## 目次

- 起草の進め方
- AC の書き方
- scope の確定
- 不足の振り分け
- steps の粒度

## 起草の進め方

1. 要求原文を言い換えずに保持し、`plan.source` に所在を記録する。
2. 対象 repository の現状を読み、要求と現状の差分から `plan.objective`（1行要約)と
   `plan.approach`（実装方針）を書く。現状を確認せずに方針を書かない。
3. 要求から AC を導出し、安定 ID を付与する。
4. scope、dependencies、constraints を確定し、確定できない事項を不足として振り分ける。
5. `plan.steps` に実装の道筋を順序付きで書く。

## AC の書き方

- AC は外部から観測可能な振る舞いとして書く。内部実装の手順や構造を AC にしない。
- 受け入れ判断が割れない判定可能な文言にする。「適切に」「正しく」など判定者によって解釈が
  変わる語を避け、入力と期待される観測結果を特定する。
- ユーザーが文言を示した場合は原文のまま保持し、言い換えない。導出した AC はレビューループと
  ユーザー確認の対象になる。
- ID は `AC-1` 形式の安定 ID とし、プラン修正で振り直さない。

## scope の確定

- `allowed_paths` / `forbidden_paths` は物理的なファイル範囲、`out_of_scope` は許可範囲内でも
  扱わない責務・作業を表す。パス制約と責務除外を混ぜない。
- repository の現状から判断できる範囲だけを書く。判断できない範囲は不足として振り分ける。

## 不足の振り分け

- AC 充足・検証可能性・scope・実行可否のいずれかに影響する blocking な不足は `open_questions` に
  する。仮定で補完して進めない。
- 影響しない minor な不足は `assumptions` に仮定・根拠つきで明示する。`rationale` には blocking で
  ない理由を書く。
- 振り分けに迷う不足は blocking として扱う。レビューループが `assumptions` の再指摘を `軽微` と
  扱うのは、この振り分けが済んでいる前提である。

## steps の粒度

- `plan.steps` は実装の道筋を示す順序付きの作業であり、実装枝への分割ではない。AC の割り当て、
  受け入れ判断の単位、revert 単位は持たせない。それらは `plan-implementation-branches` の責務で
  ある。
- 各 step は、後続の枝分割が読み替えられる程度に、対象と作業内容を特定して書く。
