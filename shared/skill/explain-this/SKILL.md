# explain-this

## 目的と境界

指定された機能の目的と全体像を明らかにし、主要な処理を実装コードと対応づけながら、その意味・条件・副作用を説明する。既存実装の理解と実装後の構成確認を扱う。
機能が何をどの順序で実現するかという「処理の流れ」と、実際のクラス・関数の呼び出し順序である「コード実行フロー」の双方を示す。
Human の意図が提示されていない場合は、実装から読み取った目的を解釈として扱う。品質判定、設計レビュー、リファクタリング提案、コード変更はこの Skill の目的に含めない。

## 説明の原則

- **全体から詳細へ**: 対象の目的と主要な処理の流れを示し、意味のある大きな処理単位に分けて実装へ対応づける。
- **実行経路への忠実さ**: 入口から主要処理まで、実在するクラス・関数の呼び出し関係と実行順序を追えるようにする。直接書かれた検証や更新は、その関数内の処理として示す。
- **意味を中心にした粒度**: 各処理が対象機能で何を実現するかを、入力・条件と結果の関係から説明する。代入・比較・加算などの操作を一つずつ日本語化するのでなく、処理の役割を捉え、重要な分岐・状態変化・副作用を示す。Router、Dispatcher、共通 Controller なども経路の連続性に必要なノードは残し、内部の説明量は対象の挙動への寄与で決める。DB更新やCookie発行は作用の意味を示し、重要な順序・トランザクション境界・失敗時挙動を保持する。
- **処理単位と実装上の責務の区別**: 一つの関数に混在する処理は意味で区切り、一つの処理が複数関数に分散する場合はまとめて説明できる。どちらも実際の実行経路との対応を保ち、理想的な責務分割へ読み替えない。責務の混在そのものを設計問題と判定しない。

## 理解の構築

開始時に `../../references/model-construction.md` と `../../references/agentic-model-construction.md` を読む。
一回の top-level invocation で explain-this が一つの task-local Local Model を所有し、Agentic Model Construction を基本に、問いに応じた理解を構築する。
処理順序、責務、データ・状態は同じモデルの目的に必要な見方として扱い、固定の処理フローモデルや永続台帳を作らない。RMO は必須依存ではない。

依頼・対象・利用可能な context から理解したい問いを捉え、コードを主な根拠に構成、主要経路、各処理の役割を調べる。
MO で現在の問いに必要な意味差と不足を観測し、caller が追加コード調査や許可された小さな確認を選ぶ。観測 projection から新しい事実や要求を追加しない。
新しい根拠は同じ Local Model へ Reintegration し、意味領域が無効になった場合だけ Recomposition と影響範囲の再観測を行う。古い理解を矛盾したまま追記しない。
説明の範囲・意味を変える Human 固有の意図や対象が不可欠なら、Method の外で explain-this が必要な点だけ確認する。調査不能を Human の選択で事実へ変換しない。
これは適応的な理解の責務であり、全項目の固定チェックリストではない。説明内容・粒度・終了判断は caller が所有する。

### 実行経路・条件・副作用の調査

依頼された機能の入口を特定し、呼び出し元、ルーティングや登録設定、実装本体を照合して主要処理までの経路を追う。
委譲、継承、動的な呼び出し先は、その接続を裏づけるコードや設定を調べる。確認できない接続は未確認として残す。
全内部呼び出しを列挙する必要はないが、省略部分がある場合も実際の呼び出し関係と順序が読み取れるようにする。

各処理について、何を受け取り、どの条件で進行・分岐・中断し、何を返すかを読み取る。データ・状態の変化や外部作用は、その条件と実装箇所に対応づける。
更新や外部送信が続く経路では、重要な実行順序、トランザクションの範囲、例外の伝播・捕捉、途中失敗で完了済みの作用がどう扱われるかを必要な範囲で追う。
呼び出し側だけで保証を判断できない場合は関連する層を調べ、調査できない範囲では原子性やロールバックを推定で保証しない。

### 全体理解から処理単位への分解

コード調査から、対象全体が何を実現し、条件・状態変化・外部作用がどうつながるかを同じ Local Model で理解する。その理解をもとに、コードを機能上意味のある処理単位へ分解する。単位は関数・クラスや操作列から決めず、対象機能の中で一つの役割として説明できる意味から決める。
一つの関数内に混在する処理は別の意味単位へ分け、一つの役割が複数関数にまたがる場合は一つにまとめる。各単位が何を実現するかを理解に基づいて説明し、該当するコードの範囲・識別子・条件を根拠として対応づける。分解で見つかった不足は同じ理解へ戻して調べ、説明のために架空の関数や呼び出し関係を作らない。
汎用基盤やライブラリの内部は、対象の条件・状態変化・失敗挙動などを説明するために必要な範囲を調べる。一般的なHTTP入出力、DI、SQL操作の仕組みの網羅は求めない。

## テストと小さな実行確認

テストは具体例・確認条件の補助根拠とする。実装の挙動、Human が意図した仕様、テストの期待値を区別し、テストが正しい仕様を表すと仮定しない。
テストがなくてもコードから分かる実装を説明する。

静的読解で重要な問いが残り、実行が判断材料を変え得る場合は、確認する問いと入力・環境を絞る。
実行前に `../../references/external-effects.md` を適用し、既存 authority の内側で小さなスクリプト等を使う。source / test / config や恒久環境を説明のために無断変更しない。
実行できない場合は、確認したかった点、理由、コードから分かる範囲、未確認部分を返す。大きな検証基盤を必須にしない。

## Human 向け出力と終了

全体理解から分解した意味上の処理単位を軸に説明を組み立て、根拠となるコードを対応づける。意味による処理のつながりと、実装の呼び出し関係を区別し、次の情報を全体から詳細へ提示する。

1. **全体像**: 対象機能の目的と、機能が何をどの順序で実現するかという主要な処理の流れ。
2. **各処理の説明とコード根拠**: 本文の中心は意味上の処理単位とする。各単位が何を実現するか、成立・失敗条件、重要な分岐・状態変化・副作用を説明し、該当するコード範囲を根拠として添える。必要に応じて順序・トランザクション境界・途中失敗時の影響も説明する。
3. **主要なコード実行フロー**: 説明の根拠を追うための参照として、入口から主要処理、正常復帰後の継続、終了・レスポンスまでを短いツリー、シーケンス図、構造化リストなどで示す。実際の呼び出し・入れ子と、同じ関数内の処理を区別し、接続に必要な基盤ノードを残す。

2 と 3 は一体として示しても、主要経路を共有の参照として示してもよい。説明の区切りは意味単位に置き、実行フローのノードごとに説明を作らない。図は意味の説明を支える経路に絞り、調査した内部呼び出しの全列挙へ広げない。補助呼び出しを省いても、残したノード間の実際の接続・順序を誤認させない。
機能としての処理のつながりと実装の呼び出し関係は区別できるようにする。見出しや記号、説明量、関数ごとの行数は固定せず、処理の意味とコード根拠の対応が読み取れる構成を選ぶ。

### 出力する詳細の選択

調査で得た理解の深さは保ち、言い換える前に出力する情報を選ぶ。フローと本文の各詳細について、それを削除すると対象機能の結果・成立条件・重要な境界、またはコード経路の追跡可能性が変わるかで判断する。どれも変わらない定数・フィールド値・補助的な内部操作や対象外の経路は、通常の説明から省く。
正確な期間が理解に不要なら「有効期限付き」と表し、期限切れでは受け付けないという条件を残す。不要な数値の単位が未確認でも、その不確実性は内部の理解に保持し、説明へ注意書きを足さない。正確な値が依頼や判断に関わる場合だけ、基準時点・単位を根拠とともに示し、不明点を限定して伝える。

本文で処理の役割・条件・作用を伝え、フローはその根拠を辿るための主要経路を示す。フローの実ノードには役割と識別子を対応づけ、処理単位の説明から必要な複数ノードや同じ関数の該当範囲へ辿れるようにする。同じ関数内の処理も入力・条件・結果の意味で表し、値の取り出し・代入・returnは独立した意味が必要な場合だけ表示する。通常はそれらを窓口の役割や、復帰後に結果を引き継ぐ段階へまとめ、実際の継続先を保つ。
処理の役割はコードと利用箇所に根拠を置き、作者の意図や未確認の業務目的を補わない。内部が未知でも、呼び出し元と利用箇所から分かる窓口の役割は示し、未確認の内部経路・条件・保証はその段階の限界として区別する。同じ識別子を本文で参照してもよいが、図の手順を再列挙するだけの文は省き、処理の意味・重要条件・作用・保証範囲を説明する。全体像と各処理の説明は保ち、同じ意味は最も伝わる箇所へまとめる。
例えば在庫計算で、入力が現在庫数と出庫数であると確認できれば、差を計算する処理は「出庫後に残る在庫数を求める」と説明できる。変数の減算と戻り値を逐語的に説明するのでなく、その計算が表す結果を伝えている。

フローでも従属的な操作は省略できるが、実際の順序、呼び出し関係、関数内の処理の所在、戻り後の重要な継続と終了が追えることを保つ。分岐は条件ラベルとして示し、その中の逐次処理を兄弟ノードに並べ、直前の関数の内部呼び出しと区別する。
失敗後の説明は、対象機能にとって重要な残存作用と保証の範囲へ絞る。ロールバックは根拠のある対象業務の更新について述べ、全状態の復元へ一般化しない。カウンタや識別子の割り当て機構は、通常は明示的に内部分析を求められた場合に扱う。

コード上の事実、特定入力・環境で実行した観測、解釈・推定、未確認情報を区別する。一条件の実行を全条件へ一般化しない。
全体像、処理の流れと実際の実行経路、各処理の意味・条件・副作用を根拠・限界付きで説明できれば終了する。重要部分を確定できなければ、分かった範囲と説明できない範囲を返し、全体確認済みとは扱わない。
説明の保存は明示された destination / write authority に従う。
出力前に、表示したフローだけを辿って、入口、主要処理の順序と呼び出し・入れ子、同じ関数内の主要処理、戻り後の継続、終了・レスポンスを確認できるかを点検する。
その経路と説明がコード根拠に一致し、重要な条件・作用・不確実性が残るかを確認する。図のノードと本文から各処理が機能上何を実現するか読み取れ、操作の逐語説明や手順の再列挙にとどまっていないかを点検する。識別子との対応と重要な条件・保証範囲は保持する。参照例との文面一致ではなく、構造・実装への忠実さ・説明粒度で判断する。
構成と意味を確定した文章へ `../../references/human-facing-projection.md` を適用し、意味保持を確認する。

## 出力の参照例

以下は記事公開APIの架空の実装を仮定した、構造と粒度の例である。実際の説明では対象コードを調べ、識別子・順序・条件・副作用とコード位置を根拠づける。例の文面・ノードや処理を回答へ当てはめるためのテンプレートにはしない。

### 責務が分離された実装

全体像: 記事を公開し、公開先を返す。
処理の流れ: 公開依頼 → 認証 → 記事取得・公開条件の確認 → 公開状態・履歴の保存 → 公開先を含むレスポンス。

- **公開対象の選別**: 認証済みの利用者による下書きの公開を受け付け、条件を満たさなければ公開せず中断する。根拠は `Auth::requireUser()`、`ArticleRepository::find()`、`Article::requireDraft()`。この処理単位は Controller と Service の呼び出し先にまたがる。
- **履歴を伴う公開の確定**: 公開状態と履歴の更新は一体で成立し、履歴を欠いた公開状態は残らない。保存失敗時はこの二つの更新を取り消して例外を伝える。根拠は `DB::transaction()` 内の `ArticleRepository::markPublished()` と `RevisionRepository::append()`。
- **公開結果の通知**: 呼び出し元へ公開成功と公開先を知らせる。根拠は `handle()` の `publish()` 正常復帰後にある応答生成・返却部分。

根拠を追う主要経路（補助的な呼び出しは省略）:

```text
public/index.php → Router::dispatch() → Controller::run() → PublishController::handle()
  handle()内:
    → Auth::requireUser() [認証]
    → PublishService::publish() [記事を公開]
        → DB::transaction() [公開状態と履歴の保存]
    → Response::created() [publish()から正常復帰後]
    → Response::withHeader('Location', 公開先) [公開先を付けた応答を返す]
  → HTTPレスポンス送信
```

### 責務が混在した実装

全体像: 認証した利用者が自分の下書きを公開し、公開先を受け取る。
処理の流れ: 公開依頼 → 認証 → 記事取得・所有者と状態の確認 → 公開状態の更新 → 履歴保存 → 公開先を含むレスポンス。

- **公開対象の選別**: 公開できるのは、認証された利用者自身の下書きに限られる。根拠は `handle()` 前半の認証・記事取得と直接記述された条件判定。
- **履歴を伴う公開の確定**: 公開状態とその履歴を残す。根拠は同じ `handle()` の `DB::markPublished()` と `DB::appendRevision()`。トランザクションと例外処理の詳細は未確認で、履歴保存の失敗時に公開状態が取り消されるかはDB層の調査を要する。
- **公開結果の通知**: 公開先を含めて成功を知らせる。根拠は同じ `handle()` 末尾の応答生成・返却部分。

三つの説明単位は同じ関数の異なる範囲に対応する。説明上分けても、実行フローは一つの `handle()` 内の直接処理として示す。

根拠を追う主要経路:

```text
public/index.php → Router::dispatch() → Controller::run() → PublishController::handle()
  handle()内:
    → Auth::requireUser() [認証]
    → 公開条件の検証 [直接記述。不成立なら中断]
    → DB::markPublished()、DB::appendRevision() [同関数内で順に公開状態と履歴を保存]
    → Response::created()、Response::withHeader() [同関数内で応答を作り返す]
  → HTTPレスポンス送信
```

### 呼び出し先の内部が未確認の場合

帳票ダウンロードAPIで、生成処理の実装だけが未提供と仮定する。

帳票生成はこの窓口の外へ委譲されている。提示された範囲で説明できるのは依頼の受付とダウンロード応答への接続までで、生成方式や生成失敗時の内部処理は確認できない。

以下は根拠となる受付関数以降の主要経路。

```text
DownloadController::handle()
  → 帳票生成の依頼: ReportAdapter::render()
    → [生成内部は未確認]
  → 生成結果をダウンロード応答にする: Response::attachment() [render()から正常復帰後]
  → ダウンロード応答を返す
```
