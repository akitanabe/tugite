# explain-this

## 目的と境界

対象機能に関わる実在の関数・クラス・構造体などを軸に、実コードのまとまった抜粋と短い補足で流れを示し、実装を書いていないHumanもコード上のつながりを追えるようにする。既存実装の理解と実装後の構成確認を扱う。
Human の意図が提示されていない場合は、実装から意図を補って適合や正しさを断定しない。説明の依頼を品質判定・改善計画・自動修復へ広げない。

## 理解の構築

開始時に `../../references/model-construction.md` と `../../references/agentic-model-construction.md` を読む。
一回の top-level invocation で explain-this が一つの task-local Local Model を所有し、Agentic Model Construction を基本に、問いに応じた理解を構築する。
処理順序、責務、データ・状態は同じモデルの目的に必要な見方として扱い、固定の処理フローモデルや永続台帳を作らない。RMO は必須依存ではない。

依頼・対象・利用可能な context から理解したい問いを捉え、コードを主な根拠に処理の流れを再構成する。
呼出し関係に加え、Middleware・設定・登録などによる暗黙の接続も必要に応じて追い、実際の実行順序、重要な分岐・成立条件、データの受渡し、状態の取得・変更を確認する。
トランザクションの開始・確定・取消と外部作用の前後関係、失敗時にどこで止まり何が残るかを、機能理解に必要な範囲で調べる。確認できない接続や順序は未確認として保持する。
MO で現在の問いに必要な意味差と不足を観測し、caller が追加コード調査や許可された小さな確認を選ぶ。観測 projection から新しい事実や要求を追加しない。
新しい根拠は同じ Local Model へ Reintegration し、意味領域が無効になった場合だけ Recomposition と影響範囲の再観測を行う。古い理解を矛盾したまま追記しない。
説明の範囲・意味を変える Human 固有の意図や対象が不可欠なら、Method の外で explain-this が必要な点だけ確認する。調査不能を Human の選択で事実へ変換しない。
これは適応的な理解の責務であり、全項目の固定チェックリストではない。説明内容・粒度・終了判断は caller が所有する。

## 実装要素と説明粒度

説明の骨格は、対象機能に関わる実在の関数・クラス・構造体などの実装要素とする。その呼出し・処理順・データ受渡しをつなぎ、各要素の内部で何をしているかを短く補足する。
コード上の構造と要素間の関係が追える範囲を選び、重要な判断・成立条件、取得・変更する状態、次の要素へ渡すものを示す。
概念的な工程を先に作って実装をそこへ組み替えず、実コードの構造に沿って処理の意味とつながりを説明する。

調査の深さと出力の粒度は分ける。共通基盤まで追って挙動を確かめても、出力には機能理解に必要な箇所を選ぶ。
Dispatcher、汎用Controller、Request/Response変換、依存生成などの詳細は通常省略できるが、判断・実行順序・状態変化・副作用・失敗時の挙動に効く箇所は残す。
クラス名やレイヤー名だけで省略を決めず、基盤自体が依頼対象なら、その基盤の処理と実装の対応を中心に説明する。

機能の結果や後続動作に関係する副作用は原則説明し、作用する対象、何をするか、実装箇所、発生条件を必要な粒度で対応づける。
たとえば DB INSERT は「セッション情報をDBに登録する」、Cookie 発行は「認証用Cookieを発行する」程度から始め、一般的な操作そのものの内部解説は要しない。
副作用の条件・順序・トランザクション境界・失敗時の扱いが機能理解に重要なら、その違いが分かるまで説明する。機能理解に影響しないデバッグログなどの付随的な作用は省略できる。

## テストと小さな実行確認

テストは具体例・確認条件の補助根拠とする。実装の挙動、Human が意図した仕様、テストの期待値を区別し、テストが正しい仕様を表すと仮定しない。
テストがなくてもコードから分かる実装を説明する。

静的読解で重要な問いが残り、実行が判断材料を変え得る場合は、確認する問いと入力・環境を絞る。
実行前に `../../references/external-effects.md` を適用し、既存 authority の内側で小さなスクリプト等を使う。source / test / config や恒久環境を説明のために無断変更しない。
実行できない場合は、確認したかった点、理由、コードから分かる範囲、未確認部分を返す。大きな検証基盤を必須にしない。

## Human 向け出力と終了

最初に実装の目的と全体像を短く示し、実装要素の呼出し・処理順に沿って、構造が追える実コードのまとまった抜粋と短い補足を示す。意図が不明なら、目的の解釈であることを明記する。
実コードを主、説明を補助とし、長い語りやコード位置一覧を説明の中心にしない。内部で行っている処理を軸に、重要な判断・変更と次へ渡す値・呼出先を追える範囲を選び、機能理解に重要な分岐、データ受渡し、状態変化・副作用、トランザクション・失敗境界を関連するコードと補足で示す。
補足はコードをまたぐ接続、重要な分岐・状態変化・実行順序へ重点を置き、引数や値はその理解に必要な箇所だけ短く説明する。見てわかる引数や単純代入の逐語説明に情報を割かず、コードを一行ずつ日本語へ翻訳したり、引数一覧・型・デフォルト値・全入力を網羅するAPIリファレンスにしたりしない。
各抜粋には出典のファイルと該当する関数・クラス・構造体など、必要に応じて行位置を添え、省略した箇所を明示する。複数の実装要素にまたがる処理は、それぞれの実コードを読み順に示し、接続を短く補足する。
抜粋は原文を保ち、別々の断片を単一の実在関数のように合成しない。説明用に改変したコードや擬似コードへ黙って置き換えず、確認できない接続は未確認として示す。
処理のつながりと判断に影響する条件・責務差を保ちながら、必要な範囲に絞る。全関数・共通基盤を無差別に載せたり、関数一覧やimport依存図だけで処理の説明を代替したりしない。図は有用な場合だけ使う。

コード上の事実、特定入力・環境で実行した観測、解釈・推定、未確認情報を区別する。一条件の実行を全条件へ一般化しない。
全体像と各処理の意味を根拠・限界付きで説明できれば終了する。重要部分を確定できなければ、分かった範囲と説明できない範囲を返し、全体確認済みとは扱わない。
確認しにくさだけで設計不良と断定しない。説明の保存は明示された destination / write authority に従う。
出力前に `../../references/human-facing-projection.md` を適用し、意味保持を確認する。固定見出し、HTML、教材、クイズ、模擬読者レビューは要求しない。
